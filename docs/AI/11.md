# PDF 面试知识重构

## 核心目标

将一本技术类 PDF 重构为一份真正适合面试复习、长期维护和快速查阅的 Markdown 文档。

不要把任务理解为普通的 PDF 转 Markdown，也不要按原文顺序逐页摘录。

最终文档应当：

- 知识结构清晰
- 章节顺序合理
- 重点突出
- 内容精炼但不缺失关键逻辑
- 适合面试时直接表达
- 适合在 GitHub、Obsidian、Typora 和 VS Code 中阅读
- 可供后续配图 Skill 继续处理

## 输入要求

输入通常是一份技术类 PDF，例如：

- JavaScript
- TypeScript
- Vue
- React
- Node.js
- 浏览器原理
- 计算机网络
- 操作系统
- 数据库
- 算法
- 前端工程化
- 综合面试题

用户也可能同时提供：

- 目标岗位
- 当前经验水平
- 重点复习方向
- 希望保留或忽略的内容
- 输出文件路径
- 已有 Markdown 文档

优先遵守用户明确给出的范围和要求。

## 输出要求

默认输出一份完整的 Markdown 文档，不拆分为多个 Markdown 文件。

文档结构应满足：

- 一级标题只作为整份文档的总标题
- 二级标题作为主要知识模块
- 三级标题作为模块内部的具体知识点
- 四级标题仅在知识点确实复杂时使用
- 不机械套用固定模板
- 不为每个小问题创建一个独立章节
- 不保留无意义的原 PDF 编号

## 第一阶段：完整读取 PDF

开始整理前，必须尽可能完整地阅读整份 PDF。

需要同时理解：

- 可提取的正文文字
- PDF 页面中的嵌入图片
- 图片中的文字
- 流程图
- 架构图
- 关系图
- 表格
- 代码截图
- 控制台输出
- 图中的箭头和关系
- 页眉、页脚与正文的区别

不能只依赖 PDF 的文本提取结果。

当文本提取出现乱码、缺字、顺序错误或图示信息丢失时，应查看对应页面的视觉内容。

不要在只阅读前几页后，就直接确定全文结构。

不要边读一页边立即生成最终文档。

应先完成整体理解，再进行知识重构。

## 第二阶段：建立全文知识地图

通读全文后，先在内部建立知识地图。

需要识别：

- PDF 主要覆盖哪些知识领域
- 哪些知识是基础概念
- 哪些知识存在前后依赖
- 哪些内容属于同一个知识模块
- 哪些内容被重复讲解
- 哪些章节顺序不合理
- 哪些内容被错误地拆散
- 哪些问题只是同一知识点的不同问法
- 哪些内容重要但原文篇幅过少
- 哪些内容篇幅很长但实际价值较低

知识地图完成前，不要正式生成最终 Markdown。

## 第三阶段：重新规划章节

不要默认沿用 PDF 原有目录。

根据全文知识体系重新规划章节。

规划时遵循：

1. 从基础知识到高级机制
2. 从概念定义到运行原理
3. 从原理到实际应用
4. 从前置知识到后续衍生知识
5. 将强关联知识放在同一模块
6. 将分散在多处的重复知识合并
7. 避免过多、过碎的章节
8. 保证不同章节之间边界清晰

例如，原文可能按以下顺序出现：

- `call`
- `apply`
- `bind`
- `new`
- `this`
- 箭头函数
- 构造函数

## 第四阶段：合并重复内容

同一知识点在 PDF 中可能多次出现。

处理重复内容时：

- 合并相同结论
- 保留最清晰的解释
- 保留最有代表性的代码
- 合并互相补充的信息
- 删除没有新增价值的重复描述
- 不因重复出现次数多，就重复写入最终文档

多个问题本质相同时，应整理成一个完整知识点。

例如：

- 什么是闭包
- 闭包有什么作用
- 闭包会导致内存泄漏吗
- 项目中在哪里使用闭包

可以合并到同一个“闭包”知识点中，并在内部区分标准回答、应用场景和常见追问。

## 第五阶段：提炼面试重点

每个知识点应优先提炼以下内容：

- 一句话理解
- 面试中可以直接表达的标准回答
- 核心原理
- 必须记住的关键词
- 有代表性的代码或示例
- 常见追问
- 易混点
- 实际开发中的意义

但不要机械地为每个知识点添加全部栏目。

简单知识点可以直接简洁说明。

复杂或高频知识点才需要完整展开。

### 简单知识点示例

### `null` 和 `undefined` 的区别

`undefined` 通常表示变量已声明但尚未赋值，或属性不存在；`null` 通常表示主动设置为空值。

面试时需要特别注意：

- `typeof undefined` 返回 `"undefined"`
- `typeof null` 返回 `"object"`，这是 JavaScript 的历史遗留问题
- `null == undefined` 为 `true`
- `null === undefined` 为 `false`

### 复杂知识点示例

### Event Loop

#### 一句话理解

Event Loop 负责协调调用栈、微任务队列和宏任务队列的执行顺序。

#### 面试回答

JavaScript 主线程会先执行当前同步代码。同步任务执行结束、调用栈清空后，运行环境会优先清空当前轮次中的微任务队列，然后再进入下一个宏任务。Promise 的 `then` 回调通常属于微任务，`setTimeout` 回调通常属于宏任务，因此 Promise 回调往往先于 `setTimeout` 执行。

#### 核心执行顺序

1. 执行当前同步代码
2. 清空微任务队列
3. 根据运行环境执行渲染或其他阶段
4. 取出下一个宏任务执行
5. 再次清空微任务队列
6. 重复上述过程

#### 常见追问

- Promise 构造函数是同步还是异步
- `async/await` 如何进入微任务队列
- 浏览器和 Node.js 的事件循环有什么区别
- 微任务不断产生会发生什么
- 为什么不能简单地说“先执行所有微任务，再执行所有宏任务”

## 面试回答规范

面试回答应接近真实口语表达，而不是教材定义。

回答应当：

- 先说结论
- 再说核心原理
- 必要时补充实际场景
- 控制无关延伸
- 避免过度书面化
- 避免只堆砌术语
- 避免出现无法继续解释的高级词汇

推荐长度：

- 简单问题：10 至 20 秒
- 普通知识点：20 至 40 秒
- 核心原理题：40 至 90 秒

不要把所有答案都扩写成长篇论文。

## 高频追问

只有在以下情况才增加“常见追问”：

- 该知识点在面试中经常连续追问
- 第一层回答容易引出更深层问题
- 原文答案只能应对表面问题
- 知识点与其他高频考点强关联
- 用户不准备追问会明显影响面试表现

适合增加追问的知识包括：

- 闭包
- 原型链
- `this`
- `new`
- Promise
- Event Loop
- async/await
- Vue 响应式
- Vue 虚拟 DOM
- React Fiber
- React Hooks
- Diff 算法
- 浏览器渲染流程
- HTTP 缓存
- TCP 三次握手与四次挥手
- 数据库索引
- 事务与隔离级别

不需要为以下简单知识机械增加大量追问：

- 基础语法定义
- 单个简单 API
- 简单类型名称
- 无实际延伸价值的事实性问题

## 易混点

当两个或多个概念容易混淆时，应明确对比。

例如：

### 易混点：`typeof`、`instanceof` 和 `Object.prototype.toString`

|方法|适用场景|主要限制|
|---|---|---|
|`typeof`|判断基础类型和函数|`null`、数组、普通对象都会出现局限|
|`instanceof`|判断对象原型链上是否存在指定原型|不适合基础类型，跨执行环境可能失效|
|`Object.prototype.toString.call()`|更精确地区分内置对象类型|写法较长，主要用于工具函数|

对比内容应简洁、可复习，不要为了表格而制造表格。

## 代码处理

保留代码时，应优先保留：

- 能直接说明核心原理的代码
- 高频手写题
- 容易产生错误理解的边界案例
- 具有代表性的实际用法

应删除或合并：

- 完全重复的代码
- 只改变变量名的重复示例
- 无助于理解的冗长业务代码
- 与当前知识点关系较弱的代码
- 明显错误且没有讲解价值的代码

必要时可以重写代码，使其：

- 变量命名更清晰
- 输出结果更明确
- 示例更短
- 更符合当前语言规范
- 更容易在面试中解释

修改原文代码后，应确保不改变其核心知识目的。

## 原文错误与过时内容

技术 PDF 可能存在：

- 语法错误
- 示例输出错误
- 已过时的浏览器行为
- 已废弃的 API
- 不严谨的定义
- 将特定环境行为误写成通用规则
- 将非严格模式行为当成现代 JavaScript 通用行为
- 对框架旧版本机制的过度泛化

发现此类问题时，不要照抄。

应优先给出准确、适用于当前环境的结论。

必要时增加：

> **补充说明（非原文）：** 原 PDF 中的描述基于旧版本、特定运行环境或非严格模式。现代项目中应以当前说明为准。

不要默默篡改会影响理解的重要结论。

也不要为了纠错而展开成与面试无关的版本考古。

## 补充内容

可以在必要时补充原文没有覆盖的内容，但必须克制。

允许补充：

- 高频追问所需的关键知识
- 原文缺失的前置概念
- 防止错误理解的边界条件
- 当前主流版本的重要差异
- 实际开发中的典型使用场景
- 能显著提高面试回答完整度的内容

补充内容应标记为：

> **补充说明（非原文）：** …

禁止：

- 无限扩展到与原 PDF 无关的领域
- 为展示知识量而加入冷门细节
- 把每个小点扩展成教程
- 大量加入未经验证的个人观点
- 让补充内容超过原始主题本身

## 图片、图表与视觉信息

当 PDF 中包含图片、流程图、关系图或表格时，应先判断其知识价值。

### 有价值的视觉信息

如果图片表达了关键关系，应将其中的信息整理进 Markdown，例如：

- 原型链关系
- Event Loop 执行流程
- 浏览器渲染流水线
- Vue 响应式依赖收集过程
- React Fiber 工作流程
- TCP 状态变化
- HTTP 缓存判断流程
- 数据库索引结构

### 无价值或装饰性图片

以下内容通常不需要保留：

- 纯装饰封面
- 与正文无关的插画
- 重复展示文字内容的截图
- 水印
- 作者头像
- 课程宣传图片

不要直接忽略所有图片，也不要把所有图片都转换为描述。

## 可视化规划

本 Skill 不负责生成插图。

本 Skill 负责判断哪些核心知识使用图示会明显比纯文字更容易理解。

只有满足以下条件之一时，才增加可视化规划：

- 存在明确的执行流程
- 存在多个对象之间的关系
- 存在层级结构
- 存在生命周期或时间顺序
- 存在复杂的状态转换
- 存在架构层次
- 存在适合并列对比的机制
- 仅靠文字容易产生理解偏差

不应标记插图的位置：

- 简单定义
- 单一结论
- 少量 API 对比
- 可以用短表格清晰说明的内容
- 图片只起装饰作用的内容

### 可视化规划格式

将可视化规划放在相关知识点内容之后。

使用以下固定格式：

> [!VISUALIZATION]  
> **类型：** flow  
> **优先级：** high  
> **标题：** Event Loop 执行流程  
> **目的：** 展示同步代码、调用栈、微任务队列和宏任务队列的执行顺序。  
> **必须表达：** 当前同步任务执行完成后先清空微任务，再进入下一个宏任务。  
> **避免表达：** 不要将所有宏任务画成一次性全部执行。

支持的类型：

- `flow`：执行流程、判断流程
- `architecture`：系统架构、模块结构
- `relationship`：对象或概念之间的关系
- `comparison`：两种或多种机制对比
- `hierarchy`：层级结构
- `lifecycle`：生命周期
- `timeline`：时间顺序
- `state`：状态变化
- `concept`：抽象概念插图

优先级：

- `high`：该图能明显提升核心知识理解，应优先生成
- `medium`：有图更好，但文字也能够理解
- `low`：一般不标记，除非用户明确要求大量配图

默认只标记 `high` 和少量 `medium`。

### 可视化规划要求

可视化规划只描述知识表达目标。

不要在此 Skill 中：

- 编写完整生图提示词
- 指定角色动作
- 指定手绘线条风格
- 指定固定 IP 角色
- 指定图片尺寸
- 生成图片文件
- 插入不存在的图片路径

这些工作交给后续的 `article-metaphor-illustrator` 或其他配图 Skill。

## Markdown 风格

使用标准 Markdown。

要求：

- 一级标题只出现一次
- 二级标题作为知识模块
- 三级标题作为具体知识点
- 代码使用带语言标识的代码块
- 简短定义使用普通段落或引用
- 对比关系可使用表格
- 流程优先使用有序列表
- 避免连续出现大量分割线
- 避免每段都使用粗体
- 避免过多 emoji
- 除重点星级外，不使用无意义装饰符号
- 保持标题命名方式统一
- 保持中英文术语格式统一

中文与英文术语第一次出现时，可使用：

- 事件循环（Event Loop）
- 词法作用域（Lexical Scope）
- 执行上下文（Execution Context）
- 虚拟 DOM（Virtual DOM）

后续可根据上下文使用中文或英文简称。

## 长文档处理

当 PDF 页数较多、无法在一次上下文中完整处理时，采用分阶段工作方式。

### 阶段一：扫描全文

先获取：

- 总页数
- 目录
- 主要主题
- 每一部分的大致页码范围
- 重复内容分布
- 图片和图表分布

### 阶段二：分段提取

按合理页码范围读取和记录内容。

分段结果只作为中间材料，不直接视为最终 Markdown。

每个分段至少记录：

- 涉及知识点
- 核心结论
- 代码示例
- 图片信息
- 可能与其他部分重复的内容
- 原文疑似错误
- 值得补充的追问
- 适合可视化的知识

### 阶段三：统一重构

所有分段读取完成后，再统一：

- 规划二级标题
- 合并重复知识
- 调整章节顺序
- 统一术语
- 统一重点等级
- 统一回答风格
- 标记可视化规划

不得把各个分段的笔记简单拼接成最终文档。

## 进度与中断恢复

处理大型 PDF 时，可以维护一个临时进度文件，例如：

```
.pdf-interview-organizer-progress.md
```

进度文件可记录：

- 已读取页码
- 未读取页码
- 已发现知识模块
- 重复内容线索
- 疑似错误
- 待核对图片
- 待补充知识
- 最终目录草案

临时进度文件不是最终交付内容。

任务完成后，如果用户不需要，应删除临时文件。

## 最终审查

生成 Markdown 后，必须进行一次整体审查。

检查以下内容：

### 结构检查

- 一级标题是否只有一个
- 二级标题是否都属于主要知识模块
- 是否存在过细的二级标题
- 章节顺序是否符合知识依赖
- 强关联知识是否被错误拆开
- 不相关知识是否被错误合并

### 内容检查

- 是否遗漏核心知识
- 是否存在重复解释
- 是否保留了无价值的原文赘述
- 面试回答是否可以直接表达
- 补充内容是否过多
- 原文错误是否得到处理
- 代码是否正确
- 术语是否统一

### 重点检查

- 是否所有内容都被错误标记为高优先级
- 五星内容是否确实属于核心必会
- 低频内容是否占据过多篇幅
- 高频追问是否真正有价值

### 可视化检查

- 是否只为真正需要图示的内容做了标记
- 可视化规划是否表达了明确知识目标
- 是否存在纯装饰性插图建议
- 是否遗漏明显需要关系图或流程图的核心机制

如发现问题，应调整后再完成任务。

## 核心原则

始终遵循以下原则：

1. 先完整理解，再开始重构。
2. 不忠于原 PDF 目录，忠于知识体系。
3. 二级标题作为主要知识模块。
4. 不逐题机械摘录，要合并同类问题。
5. 删除重复内容，但不能删除关键逻辑。
6. 面试回答应能直接说出口。
7. 高频追问按需补充，不机械扩展。
8. 发现错误或过时内容时应修正并说明。
9. 只为真正需要图示辅助理解的内容标记可视化规划。
10. 最终输出一份完整 Markdown，不拆分为大量零散文件。
11. 以提高面试复习效率为最高目标，而不是追求最大信息量。
12. 完成后必须从整体角度再次审查章节结构和知识链路。
